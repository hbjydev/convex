# CP03 OIDC research

Researched on 2026-10-09 against primary sources. This supports the implementation plan; recommendations below are not claims of implemented or tested behavior. Repository requirements come from [CP03](checkpoints.md#cp03-oidc-login-and-account-linking) and [authentication](authentication.md).

## Rust library

Recommend `openidconnect` **4.0.1**, the current published version shown by [its official crate documentation](https://docs.rs/openidconnect/latest/openidconnect/). Its async example uses `CoreProviderMetadata::discover_async`, `CoreClient::from_provider_metadata`, authorization-code flow, random state/nonce, S256 PKCE, backend code exchange, and ID-token claims verification with the expected nonce. Use these library operations rather than assembling JWT verification. The HTTP client must disable redirects: the crate explicitly warns that following them permits SSRF. [Versioned API and example](https://docs.rs/openidconnect/4.0.1/openidconnect/)

The defaults enable async `reqwest` and `rustls-tls`; the crate depends on `oauth2` 5.0.0. Prefer explicit features and commit the resulting lockfile. Check compatibility with this workspace's pinned Rust toolchain during implementation. [Published Cargo manifest](https://docs.rs/crate/openidconnect/4.0.1/source/Cargo.toml)

Keep signature, issuer, audience, expiry, and nonce checks enabled. **The library does not validate `azp`, and its default `auth_time`/`iat` callbacks accept any value.** CP03 needs an explicit authorized-party policy: reject a present `azp` different from the client ID; if multiple audiences are supported, require `azp` and explicitly trust the additional audiences. Otherwise reject multiple audiences. Require fresh `auth_time` for reauthentication and consider rejecting future `iat` beyond the chosen clock tolerance. [Verifier source](https://docs.rs/openidconnect/4.0.1/src/openidconnect/verification/mod.rs.html), [verifier hooks](https://docs.rs/openidconnect/4.0.1/openidconnect/struct.IdTokenVerifier.html)

## Protocol and account-linking rules

- Generate transaction-specific state, nonce, and S256 PKCE. Bind them to the initiating browser, server-side intent, expected issuer, and authenticated account/session when linking. RFC 9700 requires browser binding and recommends PKCE for confidential clients too. Restrict post-callback navigation to fixed application destinations. [OAuth security best practice, sections 2.1.1, 4.4, 4.7, and 4.11](https://www.rfc-editor.org/rfc/rfc9700.html)
- Use the exact `(iss, sub)` identity. Email is metadata, including when verified, and never an account-merging or membership mechanism. Validate the ID token before acting on any claims. For fresh provider authentication request `max_age=0`; unlike relying only on a visible prompt, this requires an `auth_time` claim that the backend can verify. The freshness comparison and clock tolerance remain application policy. [OIDC Core, authentication requests, token validation, and claim stability](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest)
- A fresh proof of an existing OIDC method must resolve to the already attached subject, not merely any successful provider login. Local proof must verify the current account's password. Recommendation: bind short-lived proof to the current session and the specific linking/unlinking action, then consume it once. New-method proof is a separate step. These are applications of the repository's explicit two-method proof requirement, not an OIDC-defined account-linking protocol. [Repository policy](authentication.md#identity-and-account-linking)
- Recommendation: after matching state, browser binding, expiry, intent, and configuration generation, atomically claim the pending flow before network exchange. Concurrent callbacks cannot exchange or mutate twice. A matching error callback consumes the flow too; browser mismatch must not consume another browser's valid flow. Network failure requires a new flow. Recheck session/account/invitation authority when committing the result. This persistence design applies the repository's single-use requirement; RFC 9700 does not prescribe a database schema. [Repository pending-flow and acceptance requirements](authentication.md#proposed-persisted-entities)

## Discovery and outbound HTTP

Discovery's issuer must exactly equal the configured issuer and token `iss`; do not silently rewrite trailing slashes or use an internal container hostname as a substitute issuer. Provider metadata defines the authorization, token, and JWKS endpoints. HTTPS is the production protocol requirement. [OIDC Discovery, metadata and impersonation protection](https://openid.net/specs/openid-connect-discovery-1_0.html)

Recommendation: configure one operator-controlled issuer, reject credentials/query/fragment in it, enforce HTTPS outside an explicit loopback development exception, and validate discovered endpoint URLs before use. Disable redirects for discovery, JWKS, and token requests; add timeouts and response-size limits. Disabling redirects alone does not protect against malicious endpoint URLs or DNS rebinding. Decide whether self-hosted private-network providers are supported and constrain egress accordingly; blindly banning private IPs would exclude legitimate internal IdPs. [Crate HTTP security warning](https://docs.rs/openidconnect/4.0.1/openidconnect/#security-warning)

## Reproducible development IdP

Recommend **Keycloak 26.8.0**, using `quay.io/keycloak/keycloak:26.8.0`, an optional Compose profile, loopback-bound host port, and `start-dev --import-realm`. The official quickstart uses this version and GitHub records its October 1 release. The downloads page still displayed 26.7.4 during research; use the verified release instead of that stale page. Capture and pin the image digest when implementing the fixture. [Official Docker quickstart](https://www.keycloak.org/getting-started/getting-started-docker), [26.8.0 release](https://github.com/keycloak/keycloak/releases/tag/26.8.0)

Commit a development-only `convex-realm.json` mounted read-only under `/opt/keycloak/data/import`. Define the realm, confidential client and fixed dev secret, exact application callback URI, authorization-code flow, required S256 PKCE, disabled implicit/direct grants, and fixed users/passwords. Include a user whose provider email equals a separate local account's email. Keycloak documents confidential browser clients, Standard Flow, and required S256 PKCE. [Client configuration](https://www.keycloak.org/docs/latest/server_admin/index.html#_oidc_clients), [container realm import](https://www.keycloak.org/server/containers)

Use a disposable test IdP database and deterministic realm/user identifiers so subject changes do not silently create unrelated identities between restarts. Startup import **skips an existing realm**; edited fixture JSON requires explicitly recreating the disposable service state. Keep dev and test projects/ports separate. [Realm import behavior](https://www.keycloak.org/server/importExport)

For the current host-run API/browser development topology, use one canonical issuer such as `http://127.0.0.1:8081/realms/convex`, advertised using an explicit Keycloak hostname URL. Both browser and backend must reach it. Containerized backend deployment needs a reachable canonical hostname or deliberately configured backchannel routing; do not weaken issuer validation to solve networking. [Keycloak hostname configuration](https://www.keycloak.org/server/hostname)

Add Mise tasks to start/stop the dev IdP and poll discovery readiness. Real Keycloak browser tests prove login, invitation onboarding, linking, logout, and outage behavior. A separate controlled OIDC fixture is needed for invalid signatures/claims, missing or stale `auth_time`, malicious metadata, and precise callback races; a normal IdP should not mint these invalid responses. This is a proposed verification strategy, not verified provider compatibility.

## Product decisions and remaining verification

The user selected **allow operators to require OIDC**. Enforcement across local login/signup/recovery and existing sessions, the local instance-admin recovery exception, provider-generation changes, and provider outages are application policy; neither the crate nor OIDC specifies them. Specify these in the implementation plan and test the same policy on every authentication path. Existing Convex sessions do not automatically inherit provider-side disablement or logout. [Existing session policy](authentication.md#login-and-session-implementation)

Before claiming CP03 complete: settle freshness/proof lifetimes and clock tolerance; confirm exact callback URI and Keycloak import fields against the pinned release; fetch the image digest; verify discovery/JWKS refresh behavior and outage recovery; define what counts as a usable remaining login method when enforcement or provider disablement changes; and run real provider/browser checks. No crate build, image pull, or live provider interoperability was performed for this research.
