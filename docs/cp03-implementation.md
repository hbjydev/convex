# CP03 implementation plan

Status: implementation in progress. Investigation began on 2026-10-09; the session/provider-policy foundation is implemented on 2026-10-10. OIDC login/callback, invitation onboarding, and a pinned development IdP are implemented. Fresh method proofs and linking/unlinking controls remain outstanding. [CP03](checkpoints.md#cp03-oidc-login-and-account-linking) owns completion; [authentication](authentication.md) owns the account invariants. Protocol and dependency findings are recorded in [OIDC research](cp03-oidc-research.md).

Agreed scope: one installation-level OIDC provider, with operator-enforced OIDC available for ordinary users. Enabling enforcement immediately revokes ordinary users' existing local sessions; their next protected request requires OIDC authentication. Local administrator access remains available for recovery. Workspace membership remains independent of provider claims. The decisions below are implemented; completion evidence follows the slice history.

## Recommended policy

| Concern | CP03 behavior |
| --- | --- |
| Provider scope | Agreed: one installation-level provider shared across workspaces, configured through environment variables for CP03. No provider administration UI, multiple providers, group mapping, or automatic provisioning in CP03. |
| Enforcement | Agreed: operators can require OIDC for every non-instance-admin account. Enabling enforcement immediately revokes their existing local sessions and rejects local authentication on the next protected request. Local administrators remain exempt. Optional-by-default configuration is recommended. |
| Local operator access | Instance admins retain local authentication and recovery. Prevent removing the last enabled instance admin with a local credential, including through credential unlinking or account disablement. |
| Identity resolution | Exact, case-sensitive `(issuer, subject)` resolves an existing external identity. Email is metadata and never a lookup key for account merging or membership. Allow one attached identity per account for the configured issuer in CP03. |
| New accounts | An unknown external identity needs a valid invitation. Create the account, attach the identity, consume the invitation, and grant membership in one transaction. No invitation means no account creation. |
| Existing accounts | An attached external identity logs into its existing account. Invitation acceptance uses that account. A different identity, even with equal email, creates a separate invited account or must be explicitly linked while signed in. |
| Adding a local method | Agreed: an OIDC-only account can add a local password after fresh authentication with its attached provider identity when OIDC is optional. Ordinary users cannot add a password when OIDC is required; local administrators retain this option for recovery. Account identity and memberships are preserved. |
| Invitations | Retain CP02 general capability invitations, including SMTP delivery without email binding. Provider email verification is not required for these invitations. Email-bound invitations remain deferred. |
| Session lifetime | Agreed: one environment-configurable absolute lifetime for both local and OIDC sessions, defaulting to seven days, without sliding renewal. Shortening it caps existing sessions from their original creation time; increasing it affects newly issued sessions only. Retain request-time account/membership/policy checks. Provider outage or upstream account disablement does not itself revoke issued sessions. |
| Provider changes | Agreed: removing/disabling the provider or changing issuer/client ID revokes its OIDC sessions and invalidates pending flows. Rotating the client secret preserves existing sessions but invalidates pending flows, which must restart. |
| Logout | Agreed: Convex-only logout revokes the Convex session and pending actions bound to it. The provider session remains active; require fresh provider authentication for sensitive method changes. |
| Provider outage | Agreed: existing eligible Convex sessions keep working until their normal expiry. Protected requests check Convex session/account/membership/policy state without contacting the provider. New OIDC authentication and linking fail with a recoverable error; required OIDC remains enforced and local admin recovery remains available. |

Suggested settings: `CONVEX_OIDC_ISSUER_URL`, `CONVEX_OIDC_CLIENT_ID`, `CONVEX_OIDC_CLIENT_SECRET`, `CONVEX_OIDC_DISPLAY_NAME`, `CONVEX_OIDC_ENABLED`, and `CONVEX_OIDC_REQUIRED`. Validate the complete provider tuple and boolean settings; requiring OIDC without a configured, enabled provider is an explicit configuration error. Construct the exact callback URL from `CONVEX_PUBLIC_URL`, not forwarded/request headers. HTTPS is required outside loopback development.

Use `CONVEX_SESSION_TTL_SECONDS` for the shared session lifetime, default `604800`. Validate it as a positive integer representable by database timestamp arithmetic and cookie Max-Age; malformed, zero, negative, or overflowing values are configuration errors. Session creation must explicitly derive `expires_at` and cookie Max-Age from the same configured duration, including all authentication/rotation paths. Replace the hardcoded cookie duration and update the public contract's fixed-seven-day description; preserve immutable CP02 migrations. Pending OIDC flows, fresh proofs, invitations, and recovery tokens retain their separate lifetimes.

Agreed duration-change behavior: shortening the configured lifetime persistently caps each existing session's expiry at `min(expires_at, created_at + new_duration)`, using its original creation time. Sessions older than the new limit become unusable on their next protected request. Increasing the lifetime affects newly issued sessions only; it never extends existing persisted expiry or revives sessions expired under an earlier shorter setting. Apply the cap through the shared policy transaction before the new duration becomes active across replicas. Existing browser cookies may outlast a shortened server expiry, but cannot authorize access after that expiry.

Enforcement blocks ordinary local login, local invitation signup, password change/addition, email reset and recovery issuance, and use of existing local sessions. Existing local credentials may remain attached for a later policy change, but do not count as a usable method while enforcement applies. Operator recovery must not bypass this policy for ordinary accounts. Local administrators are exempt; provider configuration must never be fetched just to execute their recovery command.

Provider configuration and enforcement use a shared persisted revision across replicas. Activation reconciles changes under the installation gate and invalidates affected sessions/flows. Each running replica holds a shared PostgreSQL advisory lease on a dedicated connection; identical settings can run together. Changing settings requires an exclusive lease, so operators must stop all old replicas before starting replicas with the new configuration. A conflicting replica fails startup rather than overwriting policy. A lost lease fails authentication and readiness until that replica is restarted. Protected requests check the active persisted policy without contacting the provider.

## Backend boundaries and persisted state

Add `crates/convex/src/oidc.rs` for provider discovery, authorization requests, code exchange, and validated identity claims. Keep user creation, login-method mutation, session issuance, and membership authorization in accounts/workspaces. Never make discovery or token requests while holding CP02's installation/account locks.

- **External identity:** UUID, user UUID, exact issuer/subject, creation time, and optional profile metadata. Enforce unique `(issuer, subject)` and the chosen per-account/issuer constraint. Do not create local credentials from claims. Missing/unusable profile names require a bounded display-name input or documented safe fallback.
- **Session provenance:** local or OIDC, optional identity reference, and provider revision. Check method/reference consistency and identity ownership in SQL. Retain durable identity rows after unlinking, or otherwise preserve historical session provenance without blocking unlinking through foreign keys.
- **Pending flow:** hashed state and browser-binding token; nonce and PKCE verifier; login/invitation/link/reauth intent; provider revision; optional target account/session, invitation reference, and existing-method proof; ten-minute expiry and consumption marker. Verifier/nonce are short-lived secrets that must remain retrievable until exchange, then be cleared. Bound creation and prune expired records.
- **Fresh proof:** short-lived, single-use, account/session/operation-bound proof of a specific attached method. Local proof verifies the current password; OIDC proof validates the exact attached issuer/subject and a fresh `auth_time`. An ordinary session is not proof of fresh control. Revoke pending proof/flows when their source session or method becomes invalid.

For callbacks, first validate state, browser binding, expiry, intent, and configuration revision; claim the flow atomically and commit consumption before exchanging the code. Only one concurrent request may exchange it. Exchange/validation failure requires a new flow. After remote validation, start a separate transaction, recheck the current policy/account/source session/inviter, and commit account, identity, membership, and session changes together. A provider failure must not consume an invitation or partially create an account.

Use authorization code with S256 PKCE, state, nonce, and query response mode. Use a dedicated host-only HttpOnly SameSite=Lax browser-binding cookie, Secure on HTTPS. Allow only fixed return destinations (`/`, `/invite`, `/account`), never a supplied arbitrary redirect. Carry invitation secrets in the POST body; persist their invitation reference server-side rather than exposing them to the provider.

Use the maintained Rust `openidconnect` library for signature, issuer, audience, expiry, and nonce verification, supplemented by the checks recorded in the research note. Bound HTTP timeouts/response sizes, disable redirects, and cache discovery/keys with controlled refresh. Provider calls belong to login/reauthentication and controlled metadata/key refresh, never ordinary protected requests. Provider unavailability must not block application startup, offline contract generation, or local admin authentication.

## Login-method changes

All method changes run under the existing control-plane transaction gate. Recheck policy and the live source session at mutation time, consume fresh proof once, revoke old sessions, and issue a fresh session through a remaining proven, eligible method.

- **Link OIDC to a local account:** freshly verify its current local password, then authenticate the new provider identity. Bind both proofs to the same account/session/operation. An identity attached to another account is a conflict; do not transfer or merge either account.
- **Add local credentials to an OIDC account:** agreed: freshly reauthenticate its attached OIDC identity, then choose a unique normalized local email and a valid password on the same account, preserving memberships. Local email remains a login identifier under CP02's policy. Allow this when OIDC is optional; block it for ordinary users when OIDC is required, while retaining the option for local administrators.
- **Unlink OIDC:** prove the remaining local method. Reject the operation if local login is barred by enforcement or no usable method remains.
- **Unlink local:** prove the remaining enabled OIDC method. Protect local administrator recovery independently of ordinary last-method checks. Remove/invalidate recovery-token rows before removing their credential reference; password reset must never recreate an unlinked credential.

An unavailable provider is not the same as a disabled provider: a configured method may remain eligible during a temporary outage, but fresh proof through it cannot succeed. Disabling/removing a provider makes its methods ineligible. Changing policy/provider configuration can intentionally lock out ordinary accounts; document required administrator checks and recovery before rollout.

## Login and invitation slice, 2026-10-10

Implemented `POST /api/v1/auth/oidc/start` and the backend GET callback using `openidconnect` 4.0.1. Browser binding, exact-origin binding, S256 PKCE, nonce, short expiry, intent separation, and committed single-use claiming protect callbacks. Starts from an authenticated browser bind to that session, so logout/revocation cancels them. Provider work occurs outside the installation transaction. Final acceptance shares invitation authority/membership validation with local onboarding and atomically commits account, identity, invitation, membership, and Convex session changes. Exact issuer/subject resolves accounts; email never participates. New identities without invitations cannot provision accounts.

The frontend offers the enabled provider on login and invitations, hides local signup under enforcement, retains administrator sign-in, and gives sanitized retry feedback. OpenAPI and generated types include the operations and safe bootstrap availability. A new immutable migration binds flows to the public origin. Request tracing omits query strings, and callback responses redirect to fixed frontend outcomes with no-referrer/no-store. Reverse proxies must independently omit authentication queries; see [operational setup](authentication.md#session-configuration-and-cp03-foundation).

Discovery/keys use a five-minute cache with a controlled unknown-key refresh at most once per 30 seconds. Network requests reject redirects, require HTTPS outside loopback, have bounded timeouts, and cap bodies at 1 MiB. Upstream tokens and exchange errors are not returned or logged. Provider availability is independent of startup and ordinary session authorization. The Compose development realm pins Keycloak 26.8.0 by image digest; Mise runs real-provider browser tests on isolated CP03 ports.

## Account-method slice (2026-10-10)

The authenticated method API and Account settings now support local-to-OIDC linking, OIDC-to-local password attachment, and removal after proving an eligible remaining method. A sixth additive migration stores operation-specific fresh proofs and flow metadata. Sensitive callbacks require fresh `auth_time`, exact attached identity for reauthentication, and the still-live initiating session; provider exchanges remain outside the control-plane transaction gate. Local proof and provider proof each have a five-minute freshness limit, with 30 seconds of provider clock tolerance.

All method mutations serialize under the existing transaction gate, rotate the session, preserve account/membership identity, and protect installation administrator recovery. Removal of local credentials deletes recovery-token rows. Identity tombstones reserve exact issuer/subject pairs to their original account, including after unlinking; original owners can reattach them. Method proofs are hashed, browser/session/action/configuration bound, and consumed atomically with successful mutation.
